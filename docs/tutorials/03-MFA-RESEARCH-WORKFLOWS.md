# Tutorial 3 — MFA, Research Identity and Programme Approval

## 1. Objective

Move beyond "a user can log in" to "a verified researcher can participate in controlled research programmes".

Authentication answers:

> Who are you?

Authorization and domain workflow answer:

> What are you allowed to do, and who is allowed to approve it?

## 2. MFA architecture

django-allauth owns MFA.

Supported types:

```text
TOTP
WebAuthn / passkeys
recovery codes
```

The project does not create its own TOTP secrets, WebAuthn protocol implementation, or recovery-code database.

That is deliberate.

## 3. TOTP

TOTP provides time-based second-factor authentication.

The implementation uses:

- six digits
- thirty-second period
- Quantum Platform issuer label

A user enrolls through allauth's MFA management flow.

## 4. Recovery codes

Recovery codes exist for loss of the normal authenticator.

They are:

- generated by allauth
- one-time use
- shown once by policy
- not a replacement for normal MFA hygiene

Students should test that a consumed code cannot be reused.

## 5. WebAuthn / passkeys

WebAuthn provides phishing-resistant authentication.

The development configuration allows an insecure origin only when:

```text
DEBUG=true
```

Production must use HTTPS.

The project has enabled the backend foundation even though the first polished Astro security page still delegates some management screens to the functional allauth UI.

This is a good MVP compromise: security functionality first, design refinement later.

## 6. Research identity

Authentication identity uses Django `User`.

Research identity uses `Person`.

This is an important distinction.

A login record should not become a dumping ground for domain-specific attributes.

`Person` stores:

- given names
- family name
- preferred name
- institution
- department
- ORCID

The relationship is one-to-one:

```text
User 1 ─── 1 Person
```

## 7. PI application

A researcher who wants to establish a programme submits a `PIApplication`.

Important fields include:

- programme name
- acronym
- description
- institution
- department
- applicant
- status
- review timestamp
- reviewing administrator

Initial state:

```text
pending
```

Only platform staff/superusers can approve or reject a PI application.

This authorization is checked in Django, not in Astro.

## 8. Atomic PI approval

Approving a PI application creates multiple related pieces of state:

```text
PIApplication
   status → approved

ResearchProgramme
   status → active
   pi     → applicant

ProgrammeMembership
   person → applicant
   role   → pi
   status → approved
```

These changes occur transactionally.

That means we avoid a half-approved system such as:

```text
programme exists
but PI membership failed
```

## 9. Existing programme membership

A normal researcher can request membership in an active programme.

The state machine is:

```text
pending
   ├── approved
   └── rejected

approved
   └── suspended
```

The programme PI is allowed to approve or reject requests for that programme.

A PI for Programme A cannot approve users into Programme B merely because they are a PI somewhere.

## 10. Audit events

Security-sensitive domain actions create audit records.

Examples:

```text
PROFILE_UPDATED
PI_APPLICATION_SUBMITTED
PI_APPLICATION_APPROVED
PI_APPLICATION_REJECTED
MEMBERSHIP_REQUESTED
MEMBERSHIP_APPROVED
MEMBERSHIP_REJECTED
```

An event records:

- actor
- event type
- object type
- object ID
- metadata
- timestamp

The audit table is intentionally simple.

It is not event sourcing. It is an accountability record.

## 11. Tested PI workflow

The Phase 2 test proved:

```text
john
  ↓
submits QCRP PI application
  ↓
AuditEvent: PI_APPLICATION_SUBMITTED

nyameko (platform admin)
  ↓
approves application
  ↓
QCRP ResearchProgramme created
  ↓
John gets role=pi, status=approved
  ↓
AuditEvent: PI_APPLICATION_APPROVED
```

This is the first complete research authorization workflow in the platform.

## 12. SSH and WireGuard key models

The schema already contains:

```text
SSHKey
WireGuardKey
```

Only public material is stored.

Never request or store:

- SSH private keys
- WireGuard private keys

The future provisioning flow should be:

```text
verified account
   ↓
MFA
   ↓
approved programme identity
   ↓
public credential registration
   ↓
controlled infrastructure provisioning
```

Infrastructure provisioning is deliberately deferred until identity and approval are authoritative.

## 13. Why UI authorization is insufficient

Imagine Astro hides an Approve button from non-PIs.

A user can still send an HTTP request manually.

Therefore:

```text
hidden button ≠ authorization
```

The Django API must evaluate:

```text
request.user
programme.pi.user
staff/superuser state
membership state
```

for every sensitive operation.

## 14. Student exercise

Use two normal users and one administrator.

1. User A submits a PI application.
2. User B attempts to approve it — expect failure.
3. Admin approves it.
4. User B requests membership.
5. User B attempts to approve their own request — expect failure.
6. User A, now PI, approves User B.
7. Inspect the audit events.
8. Attempt to reuse a recovery code.
9. Explain which controls are authentication and which are authorization.

## 15. Acceptance criteria

```text
✓ TOTP enrollment works
✓ MFA challenge works
✓ recovery code works once
✓ WebAuthn backend is enabled
✓ Person profile persists
✓ PI application can be submitted
✓ non-admin cannot approve PI application
✓ admin approval creates active programme
✓ PI receives approved PI membership
✓ researcher can request membership
✓ correct PI can approve
✓ unrelated user cannot approve
✓ AuditEvent records sensitive transitions
```
